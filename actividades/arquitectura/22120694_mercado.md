## 1. Clasificar la plataforma actual

### Diagrama de la arquitectura actual

```text
Navegador / HTML (recomendar.html) o cURL
                   │
                   │  POST /entregas/recomendar/
                   │  Content-Type: application/json
                   ▼
┌────────────────────────────────────────────────────────┐
│  Servidor Django (1 solo proceso: manage.py runserver) │
│                                                        │
│  views.py (recomendar)                                 │
│     ├── recomendador.py (Adapter / explicador)         │
│     ├── modelo_*.joblib (Árbol, Bosque o Red)          │
│     ├── reglas.py (es_posible)                         │
│     └── medios.py (crear_medio, planear)               │
└────────────────────────────────────────────────────────┘
```

- **Cliente:** El navegador web (abriendo la plantilla `recomendar.html`), una aplicación móvil o peticiones por consola con `curl`.
- **Proceso en el servidor:** Corre un único proceso de Python ejecutando Django con `python manage.py runserver` en el puerto 8000.
- **URL usada por el front:** Hace peticiones a `http://127.0.0.1:8000/entregas/recomendar/`.

**Clasificación:** La plataforma actual es un **monolito conectado por API (Monolito + API)**.

**Justificación:** Aunque el cliente se comunica enviando y recibiendo datos estructurados en formato JSON por HTTP, todo el backend corre en un único programa y bajo un solo comando. La prueba clara está en `entregas/views.py`: cuando llega la petición, la vista no hace ninguna llamada de red, sino que importa directamente los módulos en memoria con `from .recomendador import obtener_recomendador` y ejecuta `recomendador.explicar(cuerpo)`. Las reglas, el modelo `.joblib` y la lógica de transporte se ejecutan dentro del mismo espacio de memoria de Python; si el servidor se apaga o se reinicia, se cae toda la plataforma completa.

## 2. La trampa de los endpoints

Refuto totalmente lo que dice el compañero.

Tener rutas separadas como `/entregas/hola/` y `/entregas/recomendar/` solo significa que tenemos dos endpoints diferentes registrados dentro del mismo archivo `urls.py` de un solo proyecto Django. Una API únicamente separa a los clientes (el navegador o el teléfono) del servidor, pero los microservicios separan a los servidores entre sí.

Tener varios endpoints en el mismo backend es exactamente como tener varias ventanillas de atención dentro de la misma oficina: el cliente ve dos mostradores distintos, pero atrás es el mismo edificio, el mismo personal y la misma caja; si se va la luz en la oficina, todas las ventanillas se cierran al mismo tiempo. Para que fueran microservicios tendríamos que tener procesos independientes, con despliegues separados y comunicándose entre ellos por red.

## 3. La misma operación en dos mundos

Caso analizado: paquete enviado a las 3:00 de la madrugada (el modelo de IA prefiere `dron`, pero por la regla de noche se descarta y se asigna `moto`).

### Flujo en el Monolito + API de hoy:
1. El cliente envía `POST /entregas/recomendar/` con los datos del paquete.
2. La petición entra a `entregas/views.py` en la función `recomendar`.
3. `views.py` llama en la misma memoria local a `recomendador.py` con `obtener_recomendador(modelo).explicar(paquete)`.
4. `recomendador.py` evalúa el modelo `.joblib`, obtiene probabilidades donde `dron` queda en primer lugar, pero de inmediato llama a la función `es_posible` de `reglas.py`.
5. La regla detecta que la hora es 3 (horario nocturno) e invalida al dron, eligiendo al siguiente candidato viable: `moto`.
6. Enseguida, `views.py` llama a `medios.py` (`crear_medio("moto").planear(paquete)`) para calcular costo y ruta.
7. Se regresa el JSON con la respuesta final.  
Todo ocurrió por llamadas a funciones dentro de un mismo proceso de Python. Si el archivo `.joblib` no se encuentra o el recomendador falla, toda la petición HTTP del usuario truena.

### Flujo si Recomendar fuera un microservicio independiente:
1. El cliente manda `POST /pedidos` a la puerta de entrada (API Gateway), y este lo reenvía al servicio de `Pedidos`.
2. El servicio de `Pedidos` recibe la petición, pero como no sabe predecir transportes, hace un salto de red HTTP hacia `POST http://recomendar:8002/sugerir` mandando el paquete.
3. El servicio `Recomendar` (que corre en su propio contenedor y proceso separado) carga el modelo, aplica las reglas y le responde a `Pedidos` por red con `{"medio": "moto", "motivo": "..."}`.
4. `Pedidos` recibe esa respuesta por HTTP, genera el folio del envío, lo guarda y le contesta al cliente.
5. **Qué pasa si Recomendar falla:** Como son servicios separados por red, si `Recomendar` está apagado o no responde a tiempo (timeout), `Pedidos` no se cae. `Pedidos` puede manejar el fallo parcial activando un plan B (por ejemplo, asignar `camioneta` o `moto` por defecto y registrar en el pedido que la IA no estuvo disponible), o responder con un error HTTP 503 claro sin tirar la creación de pedidos en el sistema.

## 4. Decisión de la empresa

**Postura recomendada:** **Extraer únicamente el servicio de IA (microservicio `recomendar`) y mantener el resto de pedidos como monolito.**

### Argumentos:

1. **Independencia en los despliegues:** Si el modelo de Random Forest pesa 50 MB y se reentrena cada semana, tenerlo en su propio servicio permite actualizar el archivo `.joblib` y reiniciar el contenedor de IA de forma independiente. El servicio de pedidos nunca se detiene ni se reinicia, lo que evita interrupciones en la creación de pedidos de los clientes.
2. **Uso eficiente de dependencias y memoria:** El backend de pedidos es transaccional y solo necesita librerías ligeras de web y base de datos. Librerías pesadas como `scikit-learn`, `pandas` y `numpy`, junto con el modelo de 50 MB, solo se instalan y cargan en la memoria del contenedor de recomendación. Esto hace que escalar las instancias de pedidos sea mucho más rápido y barato.
3. **Aislamiento de fallos y resiliencia:** Los algoritmos de machine learning y la carga de modelos grandes son propensos a consumir mucha memoria RAM o tardar más tiempo en procesar. Si la IA llega a fallar o se satura, el servicio principal de pedidos sigue funcionando y puede tomar decisiones con reglas por defecto sin que toda la plataforma se caiga. Partir todo en más microservicios (usuarios, pagos, etc.) solo agregaría complejidad innecesaria para el tamaño actual del sistema.

## 5. Un solo corte

### Lo que se lleva el microservicio de IA (`recomendar`):
- `recomendador.py`: Toda la lógica que carga el modelo `.joblib` y traduce las probabilidades en una sugerencia.
- La carpeta `modelo/` con los archivos `.joblib` (`modelo_medios.joblib`, `modelo_bosque.joblib`, `modelo_red.joblib`).
- `reglas.py`: Las restricciones físicas y de horario (`es_posible`), para que el servicio de IA devuelva sugerencias que cumplan estrictamente con las reglas del negocio.
- Un servidor web ligero (como Flask) y un `requirements.txt` exclusivo con `scikit-learn`, `pandas` y `joblib`.

### Lo que se queda en el backend de `pedidos`:
- `views.py` y las rutas principales que reciben a los clientes y al formulario web.
- La lógica de creación de pedidos: generación de folios, registro de clientes y almacenamiento en base de datos.
- `medios.py`: Las clases de transporte (`Bicicleta`, `Moto`, `Camioneta`, `Dron`) y el método `planear()`, porque calcular tiempos de entrega y costos operativos es responsabilidad directa de la logística del pedido, no del modelo estadístico de IA.

### Justificación del corte:
Este corte separa dos responsabilidades con naturalezas y ciclos de vida completamente diferentes: la gestión de pedidos (que es transaccional, rápida y casi no cambia de código) frente a la recomendación por machine learning (que es estadística, pesada y cambia cada semana con nuevos reentrenamientos). 

No se debe hacer "un microservicio por archivo" porque partir `medios.py` o `reglas.py` en otros servicios independientes generaría un acoplamiento extremo por red, latencia innecesaria y un "monolito distribuido", que es mucho más difícil de mantener y depurar que un buen monolito modular.
